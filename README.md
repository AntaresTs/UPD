# Внимание!
Данный репозиторий **не должен содержать файлы или данные которые вы не хотите чтобы они попали в общий доступ**.

# Порядок ведения
Ветка `master` должна содержать готовую документацию/код. 
Если хотите чтонебудь дополнить или обновить, нужно создать отдельную ветку для этого, и все изменния вносить в неё. В последствии эта ветка будет объеденена в `master`.

Рекомендуется называть ветки по смыслу: `feature/...`, `fix/...`, `doc/...`.
Перед слиянием в `master` желательно, чтобы изменения просмотрел хотя бы один человек (Merge Request / Pull Request).

# Система папок
- `doc/` - вся документация. Например датащиты, статьи, книги, учебники, свои документы.
    - `datasheets/` - Даташиты
    - `literature/` - Литература, все что написанно не вами.
    - `own/` - Свои документы (самописные). Здесь же — исходники LaTeX и собранные PDF.
        - `{project}/src/` - исходные файлы конкретного документа, точка входа `main.tex`.
- `code/` - тестовый код. Например для просмотра как ЯП выполняют те или иные функции, как работают библиотеки.
    - `src/{project}/` - исходники конкретного проекта/эксперимента.
- `tmp/` - Тут любыые временные файлы, при коммите они не будут учитыватся и эта папка будет только на вашем компьютере.


# Другое

## Правила добавления файлов
- Не коммитить большие бинарные файлы без необходимости.
- Не коммитить секреты, ключи, пароли, персональные данные.
- Для временных и локальных файлов используйте `tmp/` (см. `.gitignore`).
- Названия файлов и папок — латиницей, без пробелов (пробел → `_` или `-`).
- У любого проекта (`doc/own/src/{project}/`, `code/src/{project}/`) должен быть `README.md` с кратким описанием, как собрать/запустить.

## .gitignore
В репозитории должен быть `.gitignore`, который как минимум исключает:
```gitignore
tmp/
*.aux
*.log
*.out
*.toc
*.synctex.gz
.venv/
__pycache__/
.DS_Store
```
Собранные PDF из LaTeX можно как коммитить (удобно для читателей), так и исключать — решите и зафиксируйте это правило.

## Краткий гайд по Git

### Что такое Git
Git — система контроля версий. Хранит историю изменений файлов и позволяет нескольким людям работать над одним проектом, не мешая друг другу.

### Первая настройка
Один раз на компьютере:
```bash
git config --global user.name "Ваше Имя"
git config --global user.email "you@example.com"
```

### Клонирование репозитория
Скопировать проект себе на компьютер:
```bash
git clone <url-репозитория>
cd <папка-проекта>
```

### Основной цикл работы
1. **Посмотреть состояние** — что изменено, что готово к коммиту:
```bash
git status
```
2. **Добавить изменения** в индекс (подготовить к коммиту):
```bash
git add <файл>        ## конкретный файл
git add .             ## все изменения в текущей папке
```
3. **Зафиксировать изменения** (коммит) с сообщением:
```bash
git commit -m "Краткое описание, что сделано"
```

### История
```bash
git log --oneline     ## список коммитов кратко
git diff              ## что изменено, но ещё не добавлено
git diff --staged     ## что уже добавлено, но не закоммичено
```

### Ветки
Ветка — отдельная линия работы. В `master` держим готовое, всё новое делаем в отдельных ветках.
```bash
git branch                    ## список веток
git switch -c feature/новая    ## создать ветку и перейти в неё
git switch master             ## перейти обратно в master
git branch -d feature/новая   ## удалить слитую ветку
```

### Слияние веток
Когда работа в ветке готова, её вливают в `master`:
```bash
git switch master
git merge feature/новая
```

### Синхронизация с сервером
```bash
git pull      ## забрать чужие изменения с сервера
git push      ## отправить свои коммиты на сервер
```
Первый push новой ветки:
```bash
git push -u origin feature/новая
```

### Отмена изменений (базово)
```bash
git restore <файл>            ## отменить несохранённые правки в файле
git restore --staged <файл>   ## убрать файл из индекса (до коммита)
git revert <hash>             ## отменить уже сделанный коммит новым коммитом
```

### Полезно помнить
- Коммит делать часто и с осмысленным сообщением.
- Перед началом работы — `git pull`, чтобы не разойтись с сервером.
- Никогда не коммитить секреты, пароли, ключи.
- Временные файлы держать в `tmp/` и исключать через `.gitignore`.
- Конфликты при `merge`/`pull` решаются вручную: Git помечает проблемные места в файле, нужно выбрать нужный вариант и сделать коммит.

## LaTeX
Это язык разметки компилирущейся в pdf.
В проекте используйте синтаксис для компилятора XeLaTeX.

Wiki: https://ru.wikibooks.org/wiki/LaTeX/%D0%9E%D1%81%D0%BD%D0%BE%D0%B2%D1%8B_%D1%8F%D0%B7%D1%8B%D0%BA%D0%B0_TeX

Требования к исходникам:
- Точка входа — `main.tex` в папке проекта.
- Шрифты подключаются через `fontspec` (обязательно для XeLaTeX).
- Для библиографии используйте `biber` + `biblatex`.

### Linux
Рекомендуемый редактор — **TeXstudio** (или TeXmaker): поддержка XeLaTeX и просмотр PDF «из коробки».
Сборка из консоли:
```bash
xelatex main.tex
xelatex main.tex
```
Или автоматически (рекомендуется):
```bash
latexmk -xelatex main.tex
```

### Windows
**1. Дистрибутив (обязательно).** Редактор — это только оболочка; сам XeLaTeX ставится отдельно.
- Рекомендуется **TeX Live** (полный, стабильный), установщик `install-tl-windows.bat`.
- Альтернатива — **MiKTeX** (сам доставляет отсутствующие пакеты при компиляции).
- Проверка в CMD: `xelatex -version` — должна вывести версию, а не «не найдено».

**2. Редакторы.**
- **TeXstudio** (бесплатный, рекомендуется по умолчанию): кроссплатформенный, открытый, поддержка XeLaTeX и SyncTeX. В настройках `Build` → `Default Compiler` выбрать `XeLaTeX`.
- **WinEdt** (платный/shareware): популярный исторически в Windows-среде, умеет переключать движки на XeLaTeX, богатая интеграция. Для базовых задач избыточен.

**3. Сборка из CMD:**
```bat
cd путь\к\папке\с\main.tex
xelatex main.tex
xelatex main.tex
```
Два прохода нужны для ссылок и оглавления. При использовании библиографии добавьте между ними `biber main`.

**4. Автоматизация (рекомендуется):**
```bat
latexmk -xelatex main.tex
```
`latexmk` сам определяет нужное число проходов.
